# Agent Stacks Specification

Version 0.1.0 (Draft) — 2026-09-23

A stack is an agent client, its plugins, and the runtimes both need,
built and delivered as one unit.

This is a meta specification. It does not restate what the Agent
Plugins, Agent Skills, or Model Context Protocol specifications
already say. It names them, pins the versions it composes, and
describes what a stack adds on top of them.

## 1. Status and version

This document is a draft. Version 0.1.0 marks it as not yet frozen:
anything in §5 and §6 may change.

Versions follow the pattern `spec/<major>.<minor>.<patch>.md`, one
file per released version, mirroring the layout of the Agent Plugins
specification.

A reference implementation exists in
[`agent-stacks/agent-pkgs`](https://github.com/agent-stacks/agent-pkgs)
and
[`agent-stacks/agent-stacks-cli`](https://github.com/agent-stacks/agent-stacks-cli).
It is one implementation of this document, not part of it.

Material that is not normative lives beside this document:
[RATIONALE.md](../RATIONALE.md) explains the choices made here,
[FUTURE_CONSIDERATIONS.md](../FUTURE_CONSIDERATIONS.md) records what
is not decided yet, and [UPSTREAM_PROPOSALS.md](../UPSTREAM_PROPOSALS.md)
proposes changes to the composed specifications.

## 2. Conformance language

This document is based on the existing specifications named in §4.
What it adds is the composition: which of those specifications apply
to a stack, in which versions, and how they are combined. The key
words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be
interpreted as described in RFC 2119 and RFC 8174 when, and only when,
they appear in all capitals.

## 3. Terminology

**Stack** — an agent client, zero or more plugins, and the runtimes
both need, built and delivered as one unit.

**Agent client** — what the Agent Plugins specification calls a
client: a tool that discovers, installs, loads, and executes plugin
components. Claude Code is one; so is a session manager that launches
other agent clients.

**Agent stack client** — an agent client that additionally understands
stacks: it locates a stack's plugins, adapts them to the layout its
agent expects, and launches that agent.

**Plugin** — a plugin package as defined by the Agent Plugins
specification.

**Launcher** — the executable a stack provides that starts its agent
client with the stack's plugins available. §6 describes what it does.

**Runtime** — an interpreter or executable a plugin needs in order to
run: the `python3` of a script's shebang, the `npx` of an `mcp.json`
command.

**Consumer** — the person or system that installs and runs a stack.

## 4. Composed specifications

A stack composes three specifications, pinned here at the versions
this document is written against.

### 4.1 Agent Plugins

- Source: `agentplugins/agent-plugins-spec`, pinned at commit
  `ff8ab5e392cc87bd88d87c060815a87490e51003` (2026-08-19)
- Specification documents: `spec/1.0.0.md` and `spec/1.1.0.md`
- Schemas: `schemas/1.0.0/` and `schemas/1.1.0/`

Governs the plugin package: the manifest, the standard layout,
component discovery, the `mcp.json` configuration format, and path
containment.

### 4.2 Agent Skills

- Source: `agentskills/agentskills`, `docs/specification.mdx`, pinned
  at commit `217be54` (2026-08-04)
- Rendered at <https://agentskills.io/specification>

Governs what a skill is: the `SKILL.md` file, its frontmatter fields,
and the `scripts/`, `references/`, and `assets/` directories beside
it. Agent Skills carries no version identifier, so it is pinned by
commit.

### 4.3 Model Context Protocol

- Revision `2026-07-28`
- Revision `2024-11-05`, for the legacy HTTP+SSE transport that Agent
  Plugins' `sse` transport type selects

Governs the wire behavior and lifecycle of the MCP servers a plugin
declares in its `mcp.json`.

## 5. Stack layout

### 5.1 Requirements

1. A stack is a directory rooted at a single filesystem location, the
   *stack root*. The terms "directory", "pathname", and "filename" are
   used as defined in POSIX.1-2024, Base Definitions.
2. Implementations SHOULD NOT require any file or directory at the
   stack root other than those described in this section.
3. Names of entries defined by this specification MUST match the
   following ABNF (RFC 5234):

       entry-name = 1*( ALPHA / DIGIT / "-" / "_" / "." )

   and MUST NOT be "." or "..".
4. A stack MUST compose exactly one agent client and zero or more
   plugins.
5. Plugins MUST be installed at
   `<stack root>/share/agent-plugins/<plugin-name>/`, one directory
   per plugin, each conforming to the Agent Plugins version named in
   §4.1. Plugin names MUST be unique within a stack.
6. A stack SHOULD provide one launcher executable at
   `<stack root>/bin/<stack-name>`. Running it starts the composed
   agent client with the stack's plugins available to it.
7. A stack SHOULD be transportable as one unit. How it is transported
   is left to the implementation.
8. A stack is built for one platform, such as `aarch64-darwin` or
   `x86_64-linux`. A stack is not expected to run on a platform other
   than the one it was built for.

### 5.2 A minimal stack

The smallest usable stack is one agent client, one plugin, and a
launcher. This example uses the `caveman` plugin, whose skills run
Python:

```text
caveman-stack/
├── bin/
│   └── caveman-stack              the launcher
└── share/
    └── agent-plugins/
        └── caveman/
            ├── plugin.json        the plugin's own manifest
            ├── skills/
            │   ├── caveman/SKILL.md
            │   └── ...
            └── bin/
                └── python3        link to the runtime it needs
```

## 6. Launching a stack

The layout in §5 is an interchange form, not what any particular agent
client reads. Claude Code wants `.claude-plugin/plugin.json` and one
`--plugin-dir` per plugin; another agent client wants a directory of
skill roots. The launcher, or an agent stack client acting as one,
adapts the layout to the agent client in the stack at the moment it
runs.

A launch SHOULD do four things:

1. **Read the layout.** Scan `share/agent-plugins/` once per launch,
   discovering plugins and their components at the locations Agent
   Plugins defines. Problems SHOULD be reported as warnings and what is
   valid SHOULD still load, in keeping with the non-fatal failure
   boundaries of Agent Plugins §6.2 and §7.2.2.
2. **Stage.** Produce the tree the agent client expects in a per-launch
   directory outside the stack. A launch MUST NOT write inside the
   stack, and SHOULD NOT modify the consumer's own agent client
   configuration.
3. **Resolve the agent client.** Prefer the agent client the stack
   carries. When the agent client is resolved from the consumer's
   environment instead, the launch SHOULD warn on every launch, naming
   the path it found.
4. **Exec.** Hand over to the agent client with the staged plugins
   passed in the form it takes. The launcher is not a supervisor or a
   wrapper around the session.

## 7. Open items

This section is non-normative. Each item is discussed in
[FUTURE_CONSIDERATIONS.md](../FUTURE_CONSIDERATIONS.md).

1. **Identifying a stack.** Nothing at a stack root says that it is a
   stack, which version of this specification it was built against,
   or which launcher to run. Any answer has to allow several stacks to
   be installed side by side in one merged directory, as `bin/` and
   `share/agent-plugins/` already do.
2. **Stacks composed from stacks.** How an outer stack, such as one
   whose agent client is a session manager, names the stacks it runs.
3. **Sandboxing.** Whether a sandbox policy belongs in a stack, beside
   it, or outside this specification.
4. **Secrets.** Which secrets an agent client needs, and how a stack
   refers to them without containing them.
5. **Further component types.** Hooks, subagents, stack-level rules,
   and local models, beyond the plugins a stack carries today.
