# Agent Stacks Specification

Version 0.1.0 (Draft) — 2026-09-21

A stack is an agent client, its plugins, and the runtimes both need,
built and delivered as one unit.

This is a meta specification. It does not restate what the Agent
Plugins, Agent Skills, or Model Context Protocol specifications
already say. It names them, pins the versions it composes, and
describes what a stack adds on top of them.

## 1. Status and version

This document is a draft. Version 0.1.0 marks it as not yet frozen:
the recommendations in §5 to §10 may change, and the extensions in
Appendix B are proposals that have not been submitted upstream.

Versions follow the pattern `spec/<major>.<minor>.<patch>.md`, one
file per released version, mirroring the layout of the Agent Plugins
specification this document composes.

## 2. Conformance language

This document defines no requirements of its own.

Every MUST a builder or an agent client has to satisfy comes from one of the
specifications named in §4. What this document adds is the
composition: which of those specifications apply to a stack, in which
versions, and how a builder and an agent client are recommended to combine
them. Those additions are written as recommendations, using SHOULD and
MAY as defined in RFC 2119 and RFC 8174.

A tool cannot be conformant to this document, only to the
specifications in §4. Where this document uses SHOULD, it describes
what the reference implementation does and why another implementation
is likely to want the same behavior.

## 3. Terminology

**Stack** — an agent client, zero or more plugins, and the runtimes
both need, built and delivered as one unit. §5 says what is and is not
one.

**Agent client** — what the Agent Plugins specification calls a
client, and defines in its own terminology as a tool that discovers,
installs, loads, and executes plugin components. Claude Code is one;
so is a session manager that launches one of them. This document
qualifies the word as *agent client* for readability and adds nothing
to the definition.

The term is deliberately more abstract than the industry's. An
implementation is free to call the same thing by a name its users will
recognize — the reference implementation says *harness* — as long as
the specification and the implementation agree on what they are
naming.

**Agent stack client** — an agent client that additionally understands
stacks: it locates a stack's plugins, adapts them to the layout its
agent expects, and launches that agent. Every agent stack client is an
agent client; not every agent client is an agent stack client. The
reference implementation is one of them, and is not meant to be the
only one.

**Plugin** — a plugin package as defined by the Agent Plugins
specification: a directory with a `plugin.json` manifest, skills, and
optionally an `mcp.json`.

**Launcher** — the executable a stack provides that starts its agent
with the stack's plugins available. §7 describes what it does.

**Builder** — the tool that produces a stack from pinned sources.

**Consumer** — the person or system that installs and runs a stack.

**Runtime** — an interpreter or executable a plugin's own content
needs in order to run: the `python3` of a script's shebang, the `npx`
of an `mcp.json` command.

**Dependency set** — the transitive set of files a stack needs in
order to run, including its runtimes. In the reference implementation
this is a Nix closure.

**Content-addressed store** — a filesystem location whose entries are
named by a cryptographic digest of their content and are immutable
once created. `/nix/store` is one; `/usr/bin` is not.

## 4. Composed specifications

A stack composes three specifications. This section pins the version
of each that this document is written against.

### 4.1 Agent Plugins

- Source: `agentplugins/agent-plugins-spec`
- Pinned at commit `ff8ab5e392cc87bd88d87c060815a87490e51003` (2026-08-19)
- Specification documents: `spec/1.0.0.md` and `spec/1.1.0.md`
- Schemas: `schemas/1.0.0/` and `schemas/1.1.0/`

Governs the plugin package: the manifest, the standard layout,
component discovery, the `mcp.json` configuration format, and path
containment.

The repository publishes no tags; `ff8ab5e` is the commit this
document composes and, at the time of writing, the repository head.
The reference implementation vendors that same commit.

### 4.2 Agent Skills

- Source: `agentskills/agentskills`, `docs/specification.mdx`
- Pinned at commit `217be54` (2026-08-04)
- Rendered at <https://agentskills.io/specification>

Governs what a skill is: the `SKILL.md` file, its frontmatter fields,
and the `scripts/`, `references/`, and `assets/` directories beside
it.

Agent Skills carries no version identifier and the repository
publishes no tags, so it can only be pinned by commit. `217be54` is
the most recent commit to the specification document itself; later
commits on that repository change other pages. Appendix B.5 proposes
that the specification carry a version.

### 4.3 Model Context Protocol

- Revision `2026-07-28`, current at the time of writing
- Legacy transport revision `2024-11-05`, referenced below

Governs the wire behavior and lifecycle of the MCP servers a plugin
ships. Agent Plugins defines the `mcp.json` that declares them.

A stack does not compose an MCP revision directly. `mcp.json` names
transports, and client and server negotiate the protocol version when
they connect, so the revision a stack ends up speaking is a property
of the server it launches rather than of the stack. The one revision
named normatively by reference is `2024-11-05`, which defines the
legacy HTTP+SSE transport that Agent Plugins' `sse` transport type
selects.

## 5. Stack composition

These are recommendations. An agent client is free to combine plugins
and an agent differently; this section describes the shape the reference
implementation produces and consumes.

### 5.1 What a stack is

1. A stack is a directory rooted at a single filesystem location, the
   stack root.
2. A stack SHOULD compose exactly one agent client and zero or more
   plugins. §5.4 explains why one, and what to do when you want
   several.
3. Plugins SHOULD be installed at
   `<stack root>/share/agent-plugins/<plugin-name>/`, one directory
   per plugin, each conforming to the Agent Plugins version named in
   §4.1. Plugin names SHOULD be unique within a stack.
4. A stack SHOULD provide one launcher executable at
   `<stack root>/bin/<stack-name>`. Running it starts the composed
   agent client with the stack's plugins available to it.
5. The on-disk form SHOULD be agent-client-neutral. A stack SHOULD NOT
   require the consumer to pre-adapt it to an agent client's native
   configuration layout; adapting the neutral layout to whatever the
   agent expects is the launcher's job, done at launch (§7).
6. A stack SHOULD be transportable as one unit: copying the stack and
   its dependency set to a machine that has none of the declared
   runtimes installed SHOULD yield a working stack.

Recommendation 6 is the point of the whole document, and §8 is the
mechanism that makes it achievable.

### 5.2 A minimal stack

The smallest thing worth calling a stack is one agent client, one
plugin, and a launcher. Built from the `caveman` plugin, whose skills
run Python:

```text
caveman-stack/
├── bin/
│   └── caveman-stack              the launcher
└── share/
    └── agent-plugins/
        └── caveman/
            ├── plugin.json        the plugin's own manifest
            ├── skills/
            │   ├── caveman/SKILL.md
            │   └── ...
            └── bin/
                └── python3        link to the runtime it needs
```

Nothing else is required. There is no stack-level manifest, no
per-agent-client configuration tree, and no file that names the
plugins — `share/agent-plugins/` already lists them, and each plugin
already describes itself. §11.1 covers what this costs.

### 5.3 What a stack is not

- **Not a way to declare several agent clients.** A stack is built
  around one agent, and everything else in the stack configures that
  agent. §5.4 is about this boundary.
- **Not a plugin.** A plugin is a package of components, specified by
  Agent Plugins. A stack is a plugin's delivery vehicle, together with
  an agent to run them and the runtimes both need.
- **Not a per-agent-client configuration tree.** A stack holds the
  neutral layout. `.claude/`, `.codex/` and their equivalents are
  produced at launch and belong to the launch, not to the stack.
- **Not an environment or a package manager.** A stack does not manage
  the consumer's `PATH`, shell, or project. It carries what its agent
  and plugins need and leaves the rest of the machine alone.
- **Not a sandbox.** A stack bounds what its agent brings with it,
  not what the agent can reach once running. See §11.3.

### 5.4 One agent client per stack

A stack names one agent client. Not a list, not a default with
alternatives, not a set to choose from at launch.

Read positively, that is the whole shape of a stack: pick the agent,
then configure it. The plugins it loads, the runtimes it needs, and —
as this specification grows — the sandbox it runs under and the
secrets it may reach are all configuration *around* that one agent.
Everything a stack holds is there because that agent needs it. A stack
with two agents in it has no answer to the only question a consumer
asks, which is what happens when they run it.

Three reasons the rule is worth stating rather than assuming:

1. A stack is an instance, not a menu. "Run this" is unambiguous when
   there is one thing to run.
2. The alternative multiplies. Every configuration axis added to a
   stack that holds several agents multiplies against them: three
   agents and three sandboxes is nine combinations to describe, most
   of which no one wants and none of which anyone declared.
3. Wanting several is already expressible, without any of that. Build
   one stack per agent and install them side by side; the plugins they
   share are the same packages either way.

An agent client that runs other agent clients — a session manager such
as agent deck — is composed the same way, by nesting rather than by
widening. Build a stack per agent, then compose a stack whose agent
client is the session manager and whose configuration points at those
stacks. The rule that each stack names one agent client holds at every
level.

The same move answers the case that sounds like it needs several
agents in one stack: the same plugins under two agents, or one agent
configured two ways. Those are two stacks, and what is wanted is a way
to combine them — not a stack that holds both. This version does not
specify that combination; §11.2 records it as open, and the rule above
is what any answer to it has to preserve.

## 6. Declaring a stack

§5 describes a built stack. This section describes what an author
writes to bring one into being, and it specifies a vocabulary rather
than a file format: the things a declaration has to be able to say,
and what each of them means. A builder reads that declaration in
whatever form suits it — a Nix expression, an environment manifest,
command-line arguments — and §6.5 shows the same stack declared more
than one way.

There is deliberately no file here. A serialized declaration is what
§11.1 discusses, and it belongs to the case that forces it rather than
to this version.

### 6.1 Stack fields

- `name` (required) — the stack's name, and the launcher's basename.
- `agentClient` (required) — the agent to run, and how it is
  obtained. See §6.2.
- `plugins` — the plugins to compose, each declared per §6.3.
- `runtimes` — overrides of the runtime-name to package mapping the
  builder uses. See §8.

A declaration with no plugins is legal: a stack that carries only an
agent and its runtime is a stack, and it is the thing a consumer adds
plugins to.

Two plugins in one stack SHOULD NOT share a name, because a plugin's
name is its directory under `share/agent-plugins/` and the collision
has no meaning to resolve.

### 6.2 The agent client is carried or it is borrowed

`agentClient` says two things: which agent runs, and where it comes
from. A declaration SHOULD make the second explicit rather than let it
follow from the shape of the value.

- **Carried.** The agent is part of the stack's dependency set. The
  stack runs the same agent on every machine it reaches, which is what
  §5.1(6) promises.
- **Borrowed.** The agent is resolved from the consumer's environment
  when the stack runs. Whatever is installed there runs, at whatever
  version. This is the convenient form, and an agent stack client
  SHOULD announce it at launch (§9.3).

Both are legitimate. What is not legitimate is a stack that looks
reproducible and is not, which is the failure an implicit rule invites:
where a builder infers the distinction from the type of the value it
was passed — a name means borrowed, a package means carried — the
declaration reads the same either way, and a typo silently changes
which kind of stack was built.

### 6.3 Plugin fields

A plugin in a stack is itself declared. What a builder needs from that
declaration to produce a conforming plugin (§8):

- `source` — where the plugin comes from, pinned by revision and
  content digest.
- `requiredRuntimes` — the runtime names its shebangs and `mcp.json`
  mention.
- `allowPathCommands` — commands that intentionally resolve from the
  consumer's environment rather than from the stack.
- `substitutions` — explicit rewrites for runtime references the
  format does not fix. See Appendix B.2.

`requiredRuntimes` is a record of what the plugin's content says, not a
wish list: a builder that resolves every runtime it knows about rather
than the ones this plugin names carries interpreters nothing uses.

`allowPathCommands` and `substitutions` exist because §8 refuses to
guess. Everything the builder cannot determine from the format is
declared here or not at all.

### 6.4 What a declaration does not say

- **Per-agent configuration.** Which flags Claude Code takes, where
  Codex looks for skills: these belong to the launch (§7), not to the
  stack, and a declaration that named them would bind the stack to one
  agent's current interface.
- **A sandbox, or what the agent may read.** Both are configuration
  around the agent and neither is specified yet; see §11.3.
- **A second agent client.** `agentClient` names one agent, and a
  declaration that offered a list would be describing something this
  specification does not define (§5.4). Two agents, or one agent
  configured two ways, is two declarations.
- **Nested stacks.** A meta-client's stack is declared like any other,
  with its own single `agentClient`. How an outer stack names inner
  ones is open; see §11.2.
- **Anything a plugin already says.** A plugin's manifest, its skills,
  and its `mcp.json` are the plugin's business. A stack declaration
  names the plugin; it does not restate it.

### 6.5 Bindings

This subsection is non-normative.

The reference implementation binds the vocabulary as a Nix function:

```nix
mkAgentStack {
  name = "caveman-stack";
  harness = claude-code;
  plugins = [ agent-plugin-caveman ];
}
```

`harness` is that binding's spelling of `agentClient`; passing a
package is its way of saying *carried*, and passing a bare name like
`"claude"` is its way of saying *borrowed*. The plugin fields live in
the plugin's own package, generated and pinned by an import step, not
in the stack expression.

The same implementation also composes a stack without a declaration at
all:

```sh
agent-stacks launch claude
```

which takes the plugins it finds in the active environment's
`share/agent-plugins/` and the agent named on the command line. That
is a stack assembled for the duration of one launch — the vocabulary
is the same, the lifetime is not.

A third binding is an environment manifest that installs plugin
packages and an agent, where the environment is the declaration. These
are three spellings of §6.1, and a fourth is expected rather than
discouraged.

## 7. The launcher and the layout

A stack's layout is deliberately not what any agent reads. Claude Code
wants `.claude-plugin/plugin.json` and one `--plugin-dir` per plugin;
another agent wants a directory of skill roots; a third wants
something else again. The layout in §5.1 is none of those. It is the
interchange form, and the launcher is what turns it into whatever the
agent in this stack expects, at the moment it runs.

That indirection is the reason a stack does not have to be rebuilt
when an agent changes its configuration format, and the reason one
plugin tree serves agents that disagree about everything else.

A launch does four things:

1. **Read the layout.** Scan `share/agent-plugins/` once, discovering
   plugins and their components at the fixed locations Agent Plugins
   defines. Report what is invalid and keep going: a bad component
   disables that component, not the launch.
2. **Stage.** Produce, somewhere outside the stack, the tree this
   agent expects — a generated manifest here, a directory of links
   there. The stack itself is never written to, so the same stack
   serves two agents at once, and two launches of the same agent do
   not share staging.
3. **Resolve the agent.** Prefer the agent the stack carries. A stack
   that carries one runs the same agent everywhere; a stack that finds
   one on the consumer's `PATH` runs whatever is installed there, and
   the launcher should say so rather than pretend (§9.3).
4. **Exec.** Hand over to the agent with the staged plugins passed in
   the form it takes, and get out of the way. The launcher is not a
   supervisor and not a wrapper around the session.

What the launcher deliberately does not do: mutate the consumer's
agent configuration, write inside the stack, or outlive the agent it
started.

One consequence worth stating, because it is the first thing a reader
asks. Since the staged form is derived and disposable, nothing about a
stack tells you which agent it is for by looking at
`share/agent-plugins/`. The launcher name is the only clue, and §11.1
records that gap.

## 8. Build-time runtime resolution

The reproducibility hole the composed specifications leave open: a
skill ships `#!/usr/bin/env python3`, an `mcp.json` names `node`, and
both assume the consumer machine has the right thing on `PATH`.

1. A stack SHOULD NOT depend on the consumer's `PATH` for a runtime
   that one of its plugins needs. Runtimes SHOULD be resolved when the
   stack is built and carried in its dependency set.
2. Where a plugin's content names a runtime in a position whose
   meaning is fixed by the format, a builder SHOULD rewrite that
   position to point at a runtime the stack carries. Positions whose
   meaning is not fixed by the format SHOULD be left alone, and the
   dependency declared explicitly instead. The scope argument is in
   Appendix B.2.
3. Rewritten references SHOULD point at a directory of links inside
   the plugin rather than at raw store paths. That gives a plugin one
   visible place listing its runtimes, and keeps
   `${CLAUDE_PLUGIN_ROOT}/bin/<name>` — a path an agent client can
   expand under Agent Plugins §9.2 — usable in its configuration.
4. A runtime a plugin names that the builder cannot resolve SHOULD
   fail the build, naming the file that wanted it and the name it
   wanted.

A runtime a plugin needs but does not name in either fixed position —
a binary a `SKILL.md` tells the agent to run — cannot be found this
way. Appendix B.3 proposes a declaration for those.

## 9. Agent stack client recommendations

These concern what an agent client does with a stack at launch: §7 describes
the shape of that work, and these are the choices worth repeating.

1. An agent stack client SHOULD stage plugins into a per-launch
   directory rather than mutating the consumer's agent configuration.
2. It SHOULD scan a stack's plugins once per launch and report
   problems as warnings, loading what is valid, in keeping with the
   non-fatal component failure boundaries of Agent Plugins §6.2 and
   §7.2.2.
3. It SHOULD prefer the agent the stack carries, and SHOULD say so on
   every launch when it resolved one from the consumer's environment
   instead, naming the path it found. This is a warning and not a
   failure: running the host's agent is a legitimate thing to want,
   and an unreproducible stack should announce itself rather than look
   identical to a reproducible one.
4. It MAY be configured with a set of recognized content-addressed
   store roots, and if it is, SHOULD allow a symlink inside a plugin
   root to resolve into one. The reasoning, and the proposed amendment
   that would make this conformant rather than an extension, is
   Appendix B.4.

## 10. Builder recommendations

1. A builder SHOULD pin every source it builds from by revision and
   content hash, and SHOULD NOT access the network while building.
2. A builder SHOULD pin the agent client into the stack's dependency
   set. A
   stack whose agent is resolved from the consumer's environment is
   the convenient form, not the reproducible one, and only the builder
   is in a position to make it the latter.
3. A builder SHOULD validate the plugin tree it produces against the
   Agent Plugins and Agent Skills versions in §4, and SHOULD fail the
   build rather than emit a tree that does not validate.
4. A builder SHOULD keep every path field in the plugin's
   configuration plugin-relative, as Agent Plugins §7.2.1 requires,
   even when the file it points at is a link into a store.
5. A builder SHOULD leave `assets/` alone. Those files are templates
   meant to be copied out of the plugin; a path rewritten inside one
   travels to wherever it is copied and is wrong there.

## 11. Open questions

This section is non-normative. It records what this version leaves
undecided, and why, so that a reader can tell a deliberate gap from an
oversight — and so that anyone who wants one of these answered has
somewhere to start.

### 11.1 A stack does not say that it is one

Nothing at a stack root identifies it. A directory holding
`share/agent-plugins/` and a `bin/` is probably a stack, and that is
as far as inspection gets. Two consequences follow: a tool cannot
recognize a stack without guessing, and a stack carries no record of
the specification version it was built against, so an agent client cannot
tell what it is looking at as this document changes.

A stack-level manifest — a `stack.json` naming the specification
version, the agent client, the plugins, and the launcher to run —
would close both. This version does not add one, because today the
definition of a stack lives in the thing that builds it: the Nix
expression, the Flox environment, or the CLI invocation, and each of
those already knows what it made. Adding a file that restates it would
create a second source of truth before anything reads the first.

What would force the decision is a stack that travels on its own:
installed by Homebrew or apt, or handed over as a single bundle a
consumer double-clicks. At that point something has to say which
launcher to run and which version this is, and inspection is all the
consumer has. Anyone building toward that case should expect this to
be settled before it works.

### 11.2 Stacks composed from stacks

Two cases want the same missing thing. A session manager that runs
other agents nests, as §5.4 describes: a stack per agent, then a stack
whose agent client is the session manager. And a consumer who wants
the same plugins under two agents, or one agent configured two ways,
has two stacks and no vocabulary for saying they go together.

Neither is specified here. What an outer stack would have to name, and
what a launcher would pass down to an inner one, is the open part. One
level is enough for what exists today, and whatever answers this
should leave §5.4 intact: combining stacks is not the same as a stack
that holds two agents, and the difference is the point.

### 11.3 What else configures the agent

A stack today carries plugins and runtimes. Two more axes are already
visible, and neither is specified here:

- **Sandboxing.** A stack bounds what its agent carries, not what the
  agent can reach once it runs. Whether the sandbox belongs in the
  stack, beside it, or outside this specification entirely is open.
- **Secrets.** What an agent is allowed to read, and how a stack
  refers to it without containing it, is open for the same reason.

Both are configuration around a single agent, which is the shape §5.4
describes, and both are subject to its arithmetic: an axis added to a
stack holding one agent is one more thing to declare, while the same
axis added to a stack holding several multiplies against them. That is
the property any answer here should keep.

## Appendix A: Recommendation checklist

A stack built and run as this document recommends:

- composes one agent client and zero or more uniquely named plugins
- installs plugins at `share/agent-plugins/<plugin-name>/`
- provides one launcher at `bin/<stack-name>`
- carries every runtime its plugins name in its dependency set
- rewrites only format-fixed positions, and declares the rest
- keeps configuration path fields plugin-relative
- fails its build on an unresolvable runtime, naming the file
- warns, at launch, when the agent came from outside the stack
- stages plugins per launch, leaving consumer configuration untouched
- adapts the neutral layout to the agent at launch, not at build
- writes nothing inside the stack while running

## Appendix B: Extensions proposed upstream

This appendix is non-normative.

Each item below is something the reference implementation does that
the composed specifications do not describe, or in one case forbid.
They are written as proposals to those specifications, not as house
rules. Each states what we do, why, what it costs, and where it
belongs if accepted.

### B.1 Dependencies resolved at build time

Target: Agent Plugins.

What: Rewrite the runtime references in a plugin's format-fixed
positions to point at interpreters carried in the package's own
dependency set, reached through a plugin-local `bin/` of links, so
that `${CLAUDE_PLUGIN_ROOT}/bin/<name>` is a real path.

Why: Agent Plugins describes the package. It does not say where the
`python3` in a skill's shebang comes from, so in practice it comes
from the consumer's `PATH`, and a plugin that works on the author's
machine fails or silently misbehaves on the consumer's. Resolving at
build time closes that hole without asking anything of the consumer.

Cost: Every runtime a plugin names becomes a build input of that
plugin, so the mapping table stays lean by necessity. A plugin's
dependency set grows to include its interpreters, which is the
trade being made deliberately.

Where it belongs: A section in Agent Plugins describing
build-time-resolved packages as a recognized way to build a plugin,
leaving the resolution mechanism to the builder.

### B.2 Rewrite only where the format fixes the meaning

Target: Agent Plugins.

What: Rewrite exactly two positions: a script's shebang, and a bare
`command` in `mcp.json`. Everything else — runtime names in script
bodies, in `SKILL.md` prose, in examples — is left untouched and must
be declared explicitly by the package if it matters.

Why: Those two positions are unambiguous by format: a shebang is an
interpreter reference and nothing else; an `mcp.json` `command` is a
binary to execute and nothing else. Prose is not. A rewrite that
catches `python3 -m scripts` in a script body also catches it in the
documentation next to it, and a package whose contents no longer say
what its author wrote is worse than one that fails loudly.

Cost: Body text and `SKILL.md` need per-package attention. The pass
will not guess, so some plugins need explicit substitutions written by
hand.

Where it belongs: A rule in Agent Plugins about where a builder may
rewrite, not about how much.

### B.3 Binaries a skill's markdown expects

Target: Agent Skills, with a discovery rule in Agent Plugins.

What: Let a plugin declare the binaries its markdown tells the agent
to run — `rg`, `jq`, and the like — as a list. Packaging resolves the
list; the agent client decides what to do with it.

Why: A `SKILL.md` that instructs the agent to run `rg` has a real
dependency that the format cannot express. Substitution must not guess
at it, because prose is not a fixed position (B.2), so the only way
for it to be known is for the author to say so.

Cost: A new frontmatter field, and the question of what an agent client
does when a declared binary is absent: refuse the skill, warn, or let
the agent discover the failure. This proposal deliberately leaves that
policy open.

Where it belongs: The declaration belongs in Agent Skills
frontmatter, since it is a property of the skill. Any rule about how a
plugin aggregates its skills' declarations belongs in Agent Plugins.

### B.4 Path containment and content-addressed stores

Target: Agent Plugins §4.1(3), in both 1.0.0 and 1.1.0.

What: Amend clause 3 so that a symlink inside the plugin root may
resolve to a target outside it when the target lies within a
content-addressed store root:

```text
A symlink within the plugin root MAY resolve to a target outside the
plugin root when that target lies within a content-addressed store
root. A content-addressed store root is a filesystem location whose
entries are named by a cryptographic digest of their content and are
immutable once created.

Clients MUST NOT infer store roots from the package. A client MAY be
configured with a set of recognized content-addressed store roots.
A client that recognizes a store root MUST allow symlinks resolving
into it. A client with no recognized store root MUST apply §4.1(3)
unchanged.
```

Why: Clause 3 protects two things: that a plugin can be moved and
still work, and that an agent client never reads or executes a file the
package author did not ship.

A store reference keeps the second more strongly than containment
does. A store path names its content by digest, so it cannot resolve
to content other than what the builder pinned. A path inside the
plugin root carries no such guarantee on an ordinary mutable
filesystem, where anything with write access can replace it after
install.

It keeps the first in a weaker but nameable form. Copying the plugin
directory alone leaves the link dangling; copying the plugin with its
dependency set does not. The plugin stays relocatable as a closure
rather than as a directory.

The trade is worth stating plainly, because it is the argument:

> A bare `command: "npx"` may be missing, or may silently be a
> different npx. A store reference may be missing — loudly, as a
> dangling path — but can never be a different one.

As written today, clause 3 pushes packages toward the first failure
mode and rejects the second. It rejects exactly the packages whose
provenance is strongest.

Scope: The amendment touches symlink targets only. Every path field
in the format — `command`, `cwd` — stays plugin-relative, and §7.2.1
is untouched.

Cost: An agent client must be configured before it can load such a
package, and the configuration is its operator's decision rather than
the package's. An agent client with no recognized store root behaves
exactly as it does today: under §7.2.2 the affected MCP server entry is
invalid and is dropped, while the plugin's skills keep loading. The
degradation is partial, not fatal.

Not asked for: No exception for file contents. A rewritten shebang
is content, not a path field an agent client resolves, so clause 3
does not reach it and needs no carve-out. See B.4.2.

Evidence: The subsections below report what building plugins with the
reference implementation actually produced, and what an agent client
applying Agent Plugins as written does with the result. The example
throughout is a real package, `agent-plugin-agentmemory`, whose
`mcp.json` names `npx`. `$P` stands for the plugin root inside the
store:

```text
/nix/store/<hash>-agent-plugin-agentmemory-0.9.29/
  share/agent-plugins/agentmemory
```

#### B.4.1 What a built plugin looks like, and what remains

The upstream package declares a bare command, which resolves to
whatever the consumer happens to have on `PATH`, or to nothing:

```json
{ "mcpServers": { "agentmemory": {
    "type": "stdio", "command": "npx", "args": ["-y", "@agentmemory/mcp"] } } }
```

The builder resolves `npx` at build time and rewrites the command to
a plugin-relative path, as §7.2.1 requires:

```json
{ "mcpServers": { "agentmemory": {
    "type": "stdio", "command": "./bin/npx",
    "args": ["-y", "@agentmemory/mcp"] } } }
```

That resolves against the plugin root to `$P/bin/npx`, inside the
root. Every path field in the package is plugin-relative, every
component is discoverable at its fixed location, and the manifest
validates. What remains outside the plugin root is a single link:

```text
$P/bin/npx -> /nix/store/<hash>-nodejs-22.14.0/bin/npx
```

§4.1(3) permits symlinks only where they resolve within the plugin
root, so that one link is the whole of the non-conformance, and the
whole of what this amendment asks for.

#### B.4.2 Shebangs are not a containment question

A skill script's shebang, before and after the build:

```sh
#!/usr/bin/env python3
```

```sh
#!/nix/store/<hash>-agent-plugin-caveman-2.7.0/share/agent-plugins/caveman/bin/python3
```

That string is file content. §4.1 governs paths a client discovers,
reads, or executes from the package; §4.1(5) makes values that are not
defined as paths opaque. A shebang is neither: the client reads the
file as a skill script, and the kernel resolves the interpreter. No
carve-out is needed for this pathway, which is why this amendment does
not ask for one. Files under `assets/` are skipped by the builder and keep
their original shebang.

#### B.4.3 Staging links rather than copying

The reference client stages each plugin into a per-launch directory:

```text
<cache>/launch/<agent>/<pid>/agentmemory/
├── .claude-plugin/plugin.json      generated from the spec manifest
├── skills -> $P/skills
└── bin    -> $P/bin
```

The staged root's own children resolve outside it, so the staged tree
fails §4.1(3) exactly as the store tree does.

Copying instead of linking does not fix this. A copied `bin/npx` is
still a link to `/nix/store/<hash>-nodejs-22.14.0/bin/npx`. For the
interpreter to land inside the copied root, the copy would have to
dereference it, which means copying the runtime itself into the
staging directory on every launch. Copy-out relocates the plugin root;
it does not make the package self-contained.

#### B.4.4 The clause is enforced on input and broken on output

The builder refuses a source skill that contains an escaping symlink:

```text
symlink skills/foo/data points outside the plugin (-> /etc/passwd);
every path a client reads must resolve inside the skill
```

and then writes `$P/bin/npx -> /nix/store/<hash>-nodejs-22.14.0/bin/npx`
into the output it produces.

That asymmetry is the honest framing of this proposal. The clause is right, and
the implementation agrees with it everywhere except one place, where
it breaks it to gain provenance. The request is not that the clause be
weakened but that it recognize a target whose integrity is established
by digest rather than by location.


### B.5 A version for Agent Skills

Target: Agent Skills.

What: Publish the Agent Skills specification with a version
identifier, and tag its releases.

Why: A specification that composes Agent Skills cannot say which
Agent Skills it composes. §4.2 of this document pins a commit hash
because there is nothing else to pin, which is precise but opaque:
a reader cannot tell whether two pins differ materially, and a
conformance claim cannot name what it conforms to. Agent Plugins has
versions and schemas; MCP has dated revisions. Agent Skills is the
one composed specification with neither.

Cost: Release discipline the project does not have today.

Where it belongs: The Agent Skills specification itself, mirroring
the `<major>.<minor>.<patch>` scheme Agent Plugins uses.

### B.6 Encode the `command` form in the MCP schema

Target: Agent Plugins.

What: Give `command` in `schemas/<version>/mcp.schema.json` a pattern
that admits only the two forms §7.2.1 defines — a bare executable name
or a path beginning with `./` — as `cwd` already has.

Why: §7.2.1 is prose-only. The schema types `command` as
`{"type": "string", "minLength": 1}` and defers to the specification
text in its description, while `cwd` beside it carries
`^(?:\./|\$\{PLUGIN_ROOT\}(?:/|$)|\$\{PLUGIN_DATA\}(?:/|$))`.
A builder that emitted an absolute `command` passed schema validation
and produced packages whose MCP servers a conforming client would
silently drop. The rule already exists; only its machine-readable form
is missing.

Cost: A package that violated the rule and was previously accepted by
a schema-only validator now fails validation. That is the intent, and
it is a build-time failure rather than a runtime one.

Where it belongs: The MCP schema in Agent Plugins, at the next schema
version.


## Design decisions

### Why a meta specification rather than a new format

A stack is a composition of three existing specifications. Every
requirement a builder or a client has to meet is already written down
in one of them. A fourth set of requirements would be a specification
for a specification: more text to keep in sync, and a second authority
for readers to reconcile. What was missing was not rules but the
composition — which specifications, which versions, and how they fit.

### Why a stack has no manifest yet

A stack could describe itself in a `stack.json`: the specification
version, the agent client, its plugins, the launcher to run. It would make a
stack recognizable and auditable without reading its tree, which §11.1
records as a real gap rather than a solved problem.

It is deferred, not rejected. Today the definition of a stack lives in
whatever built it — a Nix expression, a Flox environment, a CLI
invocation — and each of those already knows what it produced. A file
restating that would be a second source of truth for as long as
nothing reads the first, and a format specified before it has a
consumer is specified from imagination.

The case that decides it is a stack distributed on its own, where
inspection is all the consumer has. §11.1 says so, so that the absence
reads as a dated position rather than a preference.

### Why recommendations rather than requirements

How plugins and an agent combine into something runnable is a client
decision. The reference implementation makes one set of choices —
neutral layout in the package, adaptation at launch — and those choices
are worth writing down because another implementer will face the same
questions. They are not worth freezing into requirements that a client
with different constraints would have to violate to do its job.

### Why the extensions are in an appendix rather than integrated

Three of the five extensions propose changes to specifications this
document does not own. Writing them as requirements here would
manufacture a conflict: a package following this document would fail
Agent Plugins as published. Keeping them in a non-normative appendix
states what we want and why, while leaving the published
specifications the authority until they say otherwise.
